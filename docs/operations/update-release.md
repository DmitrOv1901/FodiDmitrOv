# Релиз обновления клиента через апдейтер

Как новая сборка клиента доезжает до игроков: сервер хранит опубликованные сборки
и подписанный манифест, клиент при старте сверяет версию, докачивает дифф и
перезапускается через внешний скрипт подмены.

## Устройство (кратко)

- **Манифест**: `GET {api}/updates/mines3/stable/manifest` — JSON со списком файлов
  (путь, sha256, размер), версией и именем сборки. Тело ответа подписано
  RSA-2048/SHA-256 (заголовок `X-Update-Signature`), публичный ключ зашит в клиенте
  (`ProjectRuntimeContracts.Update.PublicKeyPem`).
- **Файлы**: `GET {api}/updates/mines3/stable/file/{path}` — только пути из текущего
  манифеста, ETag = sha256.
- **Клиент** (`Assets/Scripts/Core/Bootstrap/Updating/`): при старте, до тяжёлой
  инициализации — проверка манифеста, дифф по `persistentDataPath/Update/state.json`,
  докачка в `staging/v{N}`, затем `apply.ps1` (бэкап → подмена → рестарт; откат при
  сбое). Сбой на любом шаге не мешает обычному старту; устаревшего клиента при
  коннекте отсечёт гейт `OutdatedClientPacket`.
- **Сервер** (`MinesServer/Server/ClientUpdatePublisher.cs`, `UpdatesController`):
  публикация zip через админ-endpoint, раздача анонимно.

## Один раз: ключ подписи

Приватный ключ лежит на сервере (`UpdateSignPrivateKeyPath`, по умолчанию
`keys/update_sign_private.pem`). В репозитории — dev-пара; её публичная половина
зашита в клиенте. **Перед продом**: сгенерировать новую пару
(`POST resources/mines-server/updates/keys/generate`), положить приватный ключ на
прод-сервер, публичный — в `ProjectRuntimeContracts.Update.PublicKeyPem` и собрать
релизный клиент (ротация ключа = новая сборка, других каналов нет).

## Чек-лист релиза

Версии — связка «int ↔ имя»: `ClientVersion = N` ↔ `0.0.N` (1 → 0.0.1, 2 → 0.0.2…).

1. **Бамп версии**: `ProjectRuntimeContracts.Networking.ClientVersion` (+1) и
   `bundleVersion` в ProjectSettings (= 0.0.N). Номер в манифесте и ClientVersion
   обязаны совпадать — их сравнивают и стартовый апдейтер, и кнопка в меню.
2. **Сборка**: Kern/Build/Windows 64 → `Build/Windows/` (Mono, x64).
3. **Публикация**: с машины сервера
   `powershell -File scripts/publish-update.ps1 -Version N -VersionName 0.0.N -Notes "..."`
   (мягкая раскатка: клиенты обновятся сами, старые продолжают играть).
4. **Проверка**: `GET {api}/updates/mines3/stable/manifest` показывает новую версию;
   запуск старого клиента прогоняет «Проверка обновлений… → Загрузка → перезапуск».
5. **Жёсткая раскатка** (опционально, когда минимум должен подняться):
   `-Enforce` — сервер поднимет `MinimumClientVersion` в config.json, клиенты ниже
   минимума получат `OutdatedClientPacket` с `ClientDownloadUrl`.

## Объявление версии без сборки (declare)

Пока билда нет, версию можно просто объявить — манифест с пустым списком файлов:

```
POST resources/mines-server/updates/declare  (form: version=1&versionName=0.0.1&notes=...)
```

Текущее состояние: задекларирована **v1 = «0.0.1»** (манифест лежит в
`MinesServer/updates/stable/` и в рабочей папке живого сервера). Клиенты v1 видят
в меню баннер «ОБНОВЛЕНИЕ НЕ ТРЕБУЕТСЯ (v0.0.1)». declare также обновляет
`ClientVersionName` (его показывает `OutdatedClientPacket`); `MinimumClientVersion`
не трогает. Если объявить vN+1, клиенты vN увидят «ТРЕБУЕТСЯ ОБНОВЛЕНИЕ v0.0.N+1»,
а кнопка «Загрузить» честно ответит «обновление ещё не опубликовано для скачивания»,
пока не прошёл настоящий publish.

## Кнопка обновления в главном меню

Баннер `UpdateAlertBanner` и модал обновления живые: `MainMenu` опрашивает
`IMenuUpdateService` (подписанный манифест против `ClientVersion`) при постройке
меню и далее раз в 30 секунд. Состояния: требуется / не требуется / не проверено
(сервер недоступен). Кнопка «Загрузить обновление» запускает реальную загрузку
диффа с прогрессом и перезапуском через apply.ps1 — тот же конвейер, что при
старте. В редакторе применение отключено (файлы установки не те), оффлайн-заглушка
пропускает проверку.

## Откат

- До жёсткой раскатки: опубликовать прошлую версию заново тем же скриптом
  (`-AllowDowngrade`), клиенты откатятся диффом.
- Локально у игрока: `<install>/.update_backup` + `rollback` вручную не нужен —
  apply.ps1 сам откатывается при сбое; неподтверждённая версия (клиент не стартанул)
  инвалидации на следующем старте, дифф перескачается.

## Ограничения

- **Player Settings → Other Settings → Allow downloads over HTTP = Always allowed**
  (`insecureHttpOption: 2`). При «Not allowed» UnityWebRequest молча отклоняет любые
  http://-запросы (манифест обновлений, бейдж онлайна) ещё до сети — меню покажет
  «Обновление не проверено». До переезда сервера на https держать Always allowed.
- Windows standalone только (на других платформах апдейтер отключён, работает
  браузер-fallback через `OutdatedClientPacket`).
- Install-каталог должен быть доступен на запись (проверяется пробой до загрузки).
- Сервер хранит последние 2 версии (retention), публикация посреди чужой загрузки
  безопасна: клиент добьёт файлы предыдущей версии.
